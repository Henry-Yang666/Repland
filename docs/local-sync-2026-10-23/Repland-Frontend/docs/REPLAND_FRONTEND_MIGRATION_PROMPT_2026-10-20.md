# Repland 前端改造指令：适配功能大改后的新项目

请直接对新项目进行前端改造，完成代码实现、真实数据接入、实际运行验证和交付。延续下述 Repland 已确认的视觉与交互风格，根据新项目的功能和后端契约重新组织页面。不要只输出设计建议、静态效果图或使用假数据的演示页面。

## 一、项目输入与工作原则

- 新项目位置：【未填写时使用当前工作目录】
- 本次新增、调整、删除的功能：【未填写时读取新项目的需求、变更记录和现有实现】
- 新后端接口、数据模型、权限及状态说明：【填写资料位置；未填写时检查接口定义、客户端、模型、服务和测试】
- 特殊要求或交付方式：【按需填写；未填写时交付本地可运行版本、修改说明和验证结果】
- 视觉参考：【可附当前版截图、录屏或源码；没有附件时按本指令实现，不因此停止任务】

先读取项目规则、README、实际技术栈、页面入口、主题组件、状态管理、路由和后端契约。先简短说明功能变化、页面调整和接入方案，然后继续实现。保留工作区已有修改，避免覆盖用户数据及无关代码。只对无法从项目中确认、会影响业务含义的缺口提出具体问题，同时推进其他工作。

需求判断原则：本次明确要求和新项目已确认的产品规范、后端契约决定功能与数据；当前 Repland 决定视觉语言与交互品质。若需求与接口相互矛盾，列出具体差异并确认关键含义，不悄悄猜测。旧文档和参考包中的历史操作命令仅供参考，不自动成为本次发布、账号或环境操作的授权。

参考视觉基线为本次已确认的前端提交 `e675277f27268534455024f43f871a1b0f7df3df`。它用于识别设计版本，不是新后端必须使用的代码基线。不要为了复用旧页面而把新后端改回旧接口、旧字段或旧状态机。

## 二、先适配新功能，再落实页面

建立“功能 → 用户操作 → 页面/组件 → 数据来源或接口 → 权限与状态 → 成功/失败反馈”的对应表，标明哪些能力继续使用、哪些需要调整、哪些已移除、哪些尚未接入。

集中处理接口模型与展示模型之间的转换。字段名、必填项、枚举、分页、优先级、日期与时区、实际时间与预计时间、撤销范围、冲突和部分成功等，均按新契约解释。显示值、计数和可用操作必须来自真实数据。

新功能应获得合理入口、完整状态及一致的视觉；删除的能力应同步清理入口和说明；替代后的流程要保持主流程连贯。尚无实现的能力明确说明依赖，不伪造可操作按钮、完成状态或接口成功回执。演示数据与真实使用分离并标注。

原参考项目是 Kotlin、Jetpack Compose、Material 3。新项目仍使用该栈时优先复用原生组件和既有架构；已经更换技术栈时，使用新项目技术栈重现同一设计语言，不为复刻界面额外更换框架。

## 三、视觉方向：淡色、协调、清楚，避免杂乱

整体使用接近白色的浅色背景、白色圆角卡片、清晰文字和克制的强调色。颜色主要用于图标底、选中态、主要操作和分组标题，通过字号、对齐、留白及细分隔线建立层次。

将以下基准集中为主题令牌，不在各页面散落硬编码：

| 用途 | 参考颜色 |
| --- | --- |
| 页面背景 | `#F7F8FC` |
| 内容卡片 | `#FFFFFF` |
| 主要文字 | `#242831` |
| 次要文字 | `#606572` |
| 通用青绿文字与图标强调 | `#326B75` |
| 日程浅蓝色族 | `#EAF2FF`，选中底可参考 `#DCEAFF` |
| 任务薄荷色族 | `#EAF7EF`，主要按钮底可参考 `#DAF2E4`，文字 `#39634D` |
| 我的与设置淡青色族 | `#E8F3F5`，与浅蓝、薄荷生成相近的更淡色阶 |
| 细分隔线与轻描边 | `#E3E6EF` |

日程以浅蓝为主，任务以薄荷为主，“我的”和设置共用青绿色系。新功能从相近色阶中扩展，避免每个按钮或卡片换一种颜色。不要按任务 ID 随机生成彩虹卡片，不要让同一事项在切页、排序或刷新时变色。颜色不能独自表达优先级、状态和风险，必须配合文字或图标。

所有大面积填充保持淡色，不使用深青、深紫等厚重主按钮。正文和图标保留足够对比度，不能为了“浅色”把文字一起调淡。成功、警告、错误和危险操作保留明确语义，但避免整页铺红或高饱和色。

渐变只使用接近白色、同色系、低对比的过渡。可以用于短资料卡片或设置分组标题；设置内容区保持白底。允许淡青、雾蓝、浅鼠尾草色之间的轻微区别，禁止再次出现粉紫资料块、蓝色总结标题、绿色总结页脚等多色拼接。

支持系统深色模式，使用对应的深色表面和清晰文字，不能直接把浅色卡片放进深色页面。普通文字对比度以至少 4.5:1 为目标，实际检查文字所在背景；不能只测色板锚点就声称所有渐变像素和交互状态均已通过。

## 四、排版与通用组件

使用中文友好的系统无衬线字体和清楚的字号层级。原生界面正文参考 14–16sp，辅助说明参考 12–14sp；标题按层级区分，时间数字对齐。其他平台使用对应的可缩放单位，不把 dp/sp 机械当作固定像素。

手机左右边距约 20dp，主要卡片圆角约 24dp，内部留白约 16–20dp，组间距约 20dp，使用统一的 4/8dp 间距体系。区分外卡片、内嵌入口和控件的圆角层级，不叠加大量描边与阴影。宽屏控制内容宽度，避免长说明横贯整屏。

主要内容左对齐；允许标题、说明和按钮文字自然换行，避免裁切、重叠和孤立的尾字。控件随内容增高，不用固定高度硬塞文字。Android 点击区域至少 48dp，其他平台遵循对应标准。保留原生点击、开关、焦点、禁用和无障碍语义；图标按钮提供可读名称，装饰图标不重复朗读。

优先形成共用组件：页面容器、分组卡片、图标底、导航行、开关行、主要/次要按钮、筛选项、表单项、空状态和错误反馈。新详情页、设置子页、弹窗和抽屉使用同一套规范。

## 五、页面组织：借鉴现状，按新业务调整

### 1. 主导航与日程

参考版本的底部主导航为“日程、任务、我的”，设置从“我的”进入，助手从相关操作入口进入。这是现有组织方式，不是新项目不可更改的限制。根据新功能重新分配入口，保持常用操作容易找到，避免把所有功能挤进导航或设置。

如果新项目仍有日程，延续“清晰日期 → 日期范围/视图切换 → 时间侧栏与事项列表”的层次。空状态给出真实可执行入口；新建、筛选、详情与返回保持一致。

如果仍保留“总计/详细”，两者应是同一份数据的不同展示：总计按真实时间处理重叠区间，详细展示完整事项和必要信息；优先级、排序和分组由新契约决定。点击时间片应能回到原始事项。单纯切换视图不应意外写入计划或改变业务状态。若新业务已取消这类视图，则调整页面，不为复刻旧版而重新创造功能。

### 2. 任务列表与详情

采用白色任务卡、淡薄荷图标和清楚的标题、状态及必要元信息。筛选项使用统一配色，主要突出选中项；类别和优先级标签保持克制。进度、状态和按钮可用性以真实数据为准。

详情按“核心信息 → 业务内容/进度/记录 → 可执行操作”组织。主要动作使用淡色填充，次要动作使用描边或文字；危险操作单独表达。新后端提供哪些动作就展示哪些动作，不固定旧版的完成、部分完成、推迟、替换、反馈等按钮。

### 3. 我的

与设置共用淡青绿色系。个人资料、内容摘要和设置入口采用统一图标、文字强调和中性卡片，保持轻浅、整洁。

若新项目保留个人资料，头像、用户名和编辑入口清楚可见；选择取消、保存失败和重试不丢失原值，软键盘不能遮挡保存或取消。头像尺寸、用户名规则、上传、本地保存与云同步都以新契约为准，不复制旧版固定限制，也不把本地成功说成已云同步。

若保留使用总结或画像，按新业务展示真实摘要、必要的更新时间与依据入口。正文、状态和依据操作通过留白与细分隔线区分，不使用多色大块背景。若这类功能已删除，则按新“我的”职责重新布局，不强加旧功能。

### 4. 设置

参考“日常使用、智能与个性化、数据与隐私”的分组方式，根据新项目实际功能调整组名和内容。只保留有真实功能支撑的分组，避免空卡片或重复入口。

外层为统一圆角白卡，分组标题使用小面积的相近淡色渐变。普通入口采用“图标 → 标题/简短说明 → 导航箭头”；开关采用“图标 → 标题/说明 → 原生开关”，对齐图标列、文字列和操作列。组内用细分隔线，避免混用大描边按钮、独立小卡片和长说明段落。

高级选项按需展开，展开/收起有清楚状态，避免同一区域重复标题。说明贴近相关控件，权限与授权信息清楚可见；版本信息置底。读取失败、保存中、保存结果和校验错误保持明确，不能用默认占位值覆盖尚未读取到的真实设置。

## 六、动效与页面连续性

复用统一的原生或框架内建动效，参考节奏：按下约 90ms、松开约 140ms、切页约 280ms、展开约 260ms、收起约 180ms。可按新平台调整，不机械追求数值一致。

- 按压缩放仅改变视觉，不缩小点击区域、不挤动布局；保留原生涟漪和焦点。
- 页面与筛选采用短距离定向过渡、轻微淡入和缩放，导航位置保持稳定。当前版可参考横向位移不超过约 32dp、纵向约 18dp。
- 快速连续切换时更新或取消旧过渡，中途展开可及时反向。退出内容不能继续接收点击，也不能出现重复操作控件。
- 点击立即触发应有动作，不等待动画结束才提交。动画和重组不得导致重复请求或重复写入。
- 返回保留合理的滚动、筛选和草稿；系统关闭动画或减少动态效果时直接显示最终状态。
- 不添加持续漂浮、闪烁或循环装饰，不在动画每帧进行网络、磁盘、排序或大图处理。

## 七、真实状态、数据接入与可靠性

主要流程覆盖实际需要的加载、空数据、有数据、局部刷新、提交中、成功、失败、权限不足和冲突等状态。网络项目按接口处理断网、超时、认证失效、分页及部分成功。

读取失败与确实没有数据必须区分；刷新尽量保留已有内容和位置。提交中防重复并保留输入，失败在相关位置提示并允许重试。保存成功以实际结果为准；若使用乐观更新，提供回滚策略。处理过期响应，避免旧请求覆盖新输入或新页面。

前端不自行制造后端未确认的完成状态、统计数值或业务规则。新契约缺失时指出具体字段、接口或能力缺口，并完成其他已明确部分。确需配套后端工作时按本次授权范围处理并说明，不擅自用旧逻辑替代。

保持组件、展示模型、状态管理和数据访问分工清楚。复用现有依赖与资源，长列表使用适合的惰性加载或分页，处理生命周期与状态恢复；基础渐变和过渡不引入大型装饰库。不要照搬旧项目的类名、数据库结构、包名、供应商地址、密钥、本机路径或模拟器名称。

如环境具备适用的 frontend-design、ui-ux-pro-max 等技能，可按实际技术栈使用；通用规则不能覆盖已确认的 Repland 方向。只有新项目确实使用 React/Next.js 或网页技术时，才应用相应网页、性能和浏览器测试规则。

## 八、实际验收与交付

完成代码后实际构建并打开应用验证，不能仅凭代码检查宣称完成。至少按本轮改动验证：

1. 新功能入口、详情、返回及真实数据流；删除或替代的功能无失效入口。
2. 新增、编辑、保存、取消、失败重试、提交防重复和状态恢复。
3. 新状态、空值、权限、时间与优先级等数据映射符合契约。
4. 我的与设置配色一致，分组标题渐变轻浅，内容区域整洁，展开后仍然易读。
5. 快速切页、连续点击、展开中途反向和系统关闭动画时，操作可靠。
6. 窄屏、横屏、较大屏幕、200% 字体、系统深色与软键盘下，文字和操作不被遮挡。
7. 本次涉及的原有流程没有回归；用隔离测试数据验证会写入或清除数据的流程。

运行适合本次变更的测试和静态检查，记录实际结果。不要沿用旧版的 218、147 或 21 等测试数量作为新项目的验证结论；构建通过、接口替身通过和真实服务验证分别说明。无法运行的检查明确说明原因和影响，不宣称已经通过。

交付：可运行的新版、修改及接口映射说明、代表性实际截图和一段实际操作录屏，以及测试结果和仍存在的具体依赖。区分真实使用与演示数据，说明启动方法和必要环境。若本次要求桌面入口，则建立或更新指向新版本的快捷方式并实际启动核对；若要求 GitHub 提交或 PR，则完成对应发布并提供链接。不要只停留在方案、占位页面或“可以继续”的说明上。

请先简短说明你对新项目、后端变化和页面调整的理解，然后直接开始执行。
